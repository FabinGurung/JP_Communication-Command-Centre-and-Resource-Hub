How to use the JP AEC Operations Hub

You do not need to think like a database engineer to use this system. The core idea is: put each fact in one correct place, validate it, then let the website/Sheets/Slack show controlled views of that same fact.

1. The mental model

Think of the system as five layers, not one giant database.

Evidence: Slack messages, Drive files, photos, site notes.

Admission: decide what is verified, ambiguous, unsupported or still pending.

Canonical machine data: CSV/JSON/JSONL + the SQL relationship contract.

Website: reads the canonical files and renders human-friendly pages.

Projections: Sheets and Slack receive controlled copies, summaries or follow-up questions.

Golden rule: never maintain the same business fact independently in five places. Edit the owning source once; regenerate/reconcile the views.

2. How to change a project master fact

Use this for project name, lifecycle/status, coordinates, company code or other public master attributes.

  1. Open projects.csv.
  2. Find the row using the stable project ID.
  3. Change only the owning field.
  4. Commit on the governed branch with a clear message.
  5. Check GitHub Actions.
  6. Open the Project Map and confirm the result.
Do not: fix a project-master fact only in a Google Sheet or directly in HTML. That creates competing truth.

3. How Daily Ops works

Daily Ops is evidence-driven. A Slack reply or photo is an input, not automatically a completed-work record.

  1. Read the provider evidence.
  2. Identify the project and date.
  3. Classify each statement: work, material, blocker, readiness, plan, instruction or evidence.
  4. Do not convert stock into consumption unless the evidence says consumption.
  5. Do not mark work DONE from an unlabeled photo.
  6. Write the current state into ops/data/current-works.json.
  7. Append the corresponding immutable event into ops/events/daily-ops-events.jsonl.
  8. Validate/deploy, then project the controlled view to Sheets and concise Slack trackers.

Current state

current-works.json answers: “What do we currently believe is true?”

History

daily-ops-events.jsonl answers: “What happened, when, and why did the current state change?”

4. How project files work

Large engineering files do not belong in the public website repository just because the page needs a link to them.

  1. Keep the actual PDF/DWG/ETABS/photo/model in Google Drive.
  2. Preserve Drive permissions there.
  3. Add the normalized project-to-file relationship to ops/data/project-resources.json.
  4. The project page can then show a permission-gated link without copying the source file into GitHub.
Drive owns bytes and permissions. GitHub owns the structured relationship metadata.

5. Why Google Sheets is still useful

Sheets is excellent for people, but not ideal as the only authority for a growing relational operations system.

Sheets is good atSheets is weak at
Fast human editingStrict PK/FK relationships
Visual reportingPreventing contradictory copies across tabs/workbooks
Simple calculationsReliable append-only event history
Field/team familiarityMulti-user application permissions and transactions

So we use Sheets as a controlled input or downstream projection where it is useful, rather than forcing it to be the only database.

6. PostgreSQL, Neon and the SQL file

What PostgreSQL is

PostgreSQL is a relational database engine. It stores tables and enforces relationships such as “every work item must belong to a valid project.”

What Neon is

Neon is a hosted PostgreSQL service. Instead of running PostgreSQL yourself, Neon provides the database server, connection endpoint, storage and related cloud features.

What this repository currently does

The current Pages site does not need a live PostgreSQL/Neon server. ops/schema/daily-ops-postgres.sql is presently a schema/relationship contract. The website reads CSV/JSON/JSONL files directly.

Then why keep a PostgreSQL schema at all?

  • It forces us to define stable IDs and foreign keys.
  • It makes relationships explicit instead of relying on memory.
  • AI can inspect a deterministic data model.
  • It gives us a clean migration path if the static files later become too limited.
  • It catches conceptual mistakes before we build a real backend.

When Neon becomes worth it

  • Several authenticated users need to edit at the same time.
  • The website itself must securely create/update records.
  • We need fast server-side queries across many tables/projects.
  • We need transactions: multiple related writes succeed or fail together.
  • We need row-level permissions, APIs, dashboards or mobile apps.
  • Data volume or automation makes file-based editing unreliable.

When CSV/JSON/Sheets are enough

  • Small team.
  • Mostly read-only public website.
  • Controlled A9/AI reconciliation.
  • Low simultaneous write volume.
  • Git history is useful and acceptable as change history.

7. What happens when we publish

  1. A governed file changes on the working branch.
  2. GitHub Actions validates required IDs, formats and constraints.
  3. If validation fails, the site should not be treated as successfully updated.
  4. If it passes, GitHub Pages publishes the branch preview.
  5. Open the site and visually confirm the result.
  6. Only promote to main when that release is explicitly approved.

8. Recovery and A9 safety

A9 governance is there so a convenient edit does not silently erase history or overwrite another writer.

  • PRE snapshot: rollback point before a material mutation.
  • Lease/current-head check: avoid writing over concurrent work.
  • Append-only history: preserve why the change happened.
  • Provider readback: verify the external system actually contains what we think we wrote.
  • POST snapshot: preserve the verified after-state.
  • Local/Main acknowledgement: only advance the synchronization cursor after exact readback.
A9 does not mean “duplicate everything forever.” It means preserve enough lineage and rollback evidence to safely reproduce, audit and recover the important state.

9. Simple rule for choosing storage

If the thing is…Use
A small clean table used directly by the static siteCSV
Nested current application stateJSON
An append-only history streamJSONL
A large/source engineering documentGoogle Drive
Something staff must easily edit/reviewGoogle Sheets, then reconcile
A multi-user secure transactional applicationPostgreSQL/Neon + authenticated backend
