# Memory Wall instruction — JP version control — V000001

Use this as an operating instruction for future AI sessions. Read current live
manifests and branch rules before acting; this instruction does not authorize
access to unrelated files or publication of private information.

> In JP, version control means preserving one identifiable live authority while
> making every meaningful change traceable and reversible. It does not mean
> making another editable copy for the same facts.

Copyable prompt:

```text
Follow these JP version-control rules for every file, Sheet, notebook and website change.

1. Find and inspect the existing owner first. Use the Drive inventory, starred
   Sheets, live manifest and known source IDs. Do not ask me to locate files that
   the inventory or connected tools can locate. Reuse a populated owner. An empty
   template is not a second authority. Create a missing owner only after checking
   existing candidates, and populate it from traceable evidence.

2. Keep one LIVE Google Drive object for each subject. Preserve its file ID,
   URL, record IDs and effective access when renaming, reorganizing or updating.
   One subject has one owning data table; manifest, instructions and version
   history tabs are supporting controls. Pages and Excel outputs reuse that
   authority. They do not become independent places to edit the same facts.

3. Before a meaningful live change, create an enumerated PRE snapshot. After
   validation, create the corresponding POST snapshot and verify it. Name them
   V000001, V000002, and so on, with PRE or POST and an accurate change label.
   Use the next unused version for that artifact. Never renumber old history,
   replace a sealed snapshot, or make a new version solely to resend a link.

4. Put all snapshots, superseded copies, rollback files and historical notebooks
   in that source's dedicated folder under the central 01_JP Archive Gallery.
   Never mix PRE, POST or old versions into the live working folders. Reuse the
   same archive folder by stable source ID even if the source is renamed. Keep
   archive folders separate for separate sources, including Paras and Shiv.

5. Inside each live Google Sheet, maintain a readable Manifest and append-only
   Version History. Record: purpose, stable live ID, owning data tab, source and
   publishing relationships, current version, date/time/time zone, what changed,
   why, PRE/POST links, validation actually performed, pending checks and exact
   restore instructions. Preserve existing entries and link to original evidence.
   Name records and headings so a human can understand them without a schema.

6. Restore into the SAME live ID from the verified archive. Preserve later
   history and document the restore as a new version. Do not switch all users
   to an archived copy or silently make a replacement live workbook.

7. Keep original messages/files in dedicated Drive source folders, with original
   Slack/Discord/direct-chat provenance, timestamps and labels. Derive readable
   work, material and supervision bullets separately. Preserve quoted originals.
   Do not infer quantities, costs, completion, approval or engineering acceptance.
   Unknown stays unknown; an unchecked box is not proof of absence.

8. Humans edit source Sheets. Automatically assemble one publishing workbook
   per repository from those owners. Validate and read back the joined data,
   then generate the approved JSON in GitHub Actions and deploy GitHub Pages.
   CSV, JSON and Excel are generated views/exports. Record their source version.
   Source data and private raw evidence stay in Drive; maintained transformation,
   rendering and validation code belongs in GitHub. No credentials in either
   public code, Sheet cells, notebook outputs or exported navigation files.

9. Actions' routine publishing history may use the documented, existing
   append-only restore log when its service identity cannot own My Drive copies.
   Each entry must identify the source/live object, run, sequence, digest and
   restorable PRE state; never rewrite old entries. This exception applies to
   generated publishing refreshes, not to replacing native human-source PRE/POST
   archives with another editable source workbook.

10. Use the registered Git branch/PR lane. Preserve other people's work. Do not
    force-push, mutate frozen archive branches or promote main without the
    governed release process. Git commits, notebook versions, Sheet versions and
    milestone tags have separate version sequences. V8 inventory is not V8 data
    and is not a website release. State which artifact each version describes.

11. A current self-contained notebook replaces older notebook code; do not tell
    me to run V5, then V6, then V8 unless an explicit verified migration requires
    it. Reuse the live notebook ID when changing that notebook's purpose-preserving
    implementation. Give a genuinely different task its own clearly named
    notebook and version history. Keep keys/tokens out of saved notebook outputs.

12. Report facts, not intentions: distinguish prepared code, offline tests,
    connected API assembly, successful live Actions fetch, deployed Pages and
    release-tag completion. A successful snapshot deployment is not a live Sheet
    refresh. Link the actual run and its matching deployed receipt. Never mark
    an unrun notebook or an unreviewed source queue complete.

13. Deliver human instructions and navigation as readable HTML stored in Drive,
    with a table of contents, summaries and links to exact live Sheets/folders.
    Drive's HTML preview may not execute scripts; provide a native Sheet entry
    point as well. Do not make ChatGPT download history the only way to get files.

14. Leave 98_INTAKE_STAGING outside broad scans/edits while I am working there.
    Keep the Discord collector paused unless I explicitly restart it. Check
    current instructions for any later change to these boundaries.

When handing off, list the live IDs/links, exact artifact versions, PRE/POST
locations, code commit/PR, checks actually passed and concrete remaining blockers.
Continue routine authorized work without repeatedly asking permission.
```
